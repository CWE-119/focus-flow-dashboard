# Windows releases and auto-updates

FocusFlow publishes Windows builds from
[`CWE-119/focus-flow-dashboard`](https://github.com/CWE-119/focus-flow-dashboard).
The release workflow runs on Windows so Electron packages the correct native
SQLite binary.

## Build types

- `FocusFlow Setup <version>.exe` is the NSIS installer. Use this build for
  installed-app auto-updates.
- `FocusFlow <version>.exe` is portable and must be updated manually.
- `latest.yml` and the installer `.blockmap` are update metadata. They must be
  generated by the same build as the installer.

`npm run build:electron:win` creates local files in `dist_electron/`; it does
not publish a GitHub release.

## Automated release flow

The workflow in `.github/workflows/release-windows.yml` runs for tags matching
`v*.*.*`. It verifies the tag and package version, installs locked dependencies,
runs the release checks, uploads all assets to a draft release, and publishes
the release only after the upload completes.

From a clean `main` branch:

```bash
npm run release:check
npm version patch -m "Release v%s"
git push origin main --follow-tags
```

Use `minor` or `major` instead of `patch` when the release warrants it. Never
reuse a published version or tag because update metadata contains checksums for
one specific build.

After the workflow succeeds, confirm the release contains:

- the NSIS Setup executable referenced by `latest.yml`;
- the matching installer `.blockmap`;
- `latest.yml`;
- the portable executable, when a portable build is being offered.

The local filename may contain spaces while the GitHub asset uses a safe name.
Let electron-builder publish the files together rather than uploading one EXE
manually.

## Manual fallback

Use this only on Windows when the tag workflow cannot be used. Keep a
fine-grained GitHub token with Contents read/write access in the current
PowerShell process only:

```powershell
$env:GH_TOKEN = "your-temporary-token"
npm run release:check
npm run publish:electron:win
gh release edit "v<version>" --draft=false --latest
Remove-Item Env:GH_TOKEN
```

The publish command deliberately uses `--publish always`. The release remains
draft during upload because `electron-builder.json` sets `releaseType` to
`draft`.

## Verify the real updater path

Test on a clean Windows VM before announcing a release:

1. Install the NSIS build for the previous version.
2. Publish a higher version from the canonical repository.
3. Launch the older installed app.
4. Confirm the update-available and update-downloaded prompts appear.
5. Install the update and confirm the app restarts on the new version.
6. Confirm the local backend starts and existing SQLite data remains intact.

Also inspect the packaged SQLite binding:

```bash
file dist_electron/win-unpacked/resources/app.asar.unpacked/node_modules/sqlite3/build/Release/node_sqlite3.node
```

It must report a Windows `PE32+` binary, not a Linux `ELF` binary. The packaged
archive should contain `backend/index.js` and the Express dependency, and
`resources/app-update.yml` should point to the canonical repository.

## Signing

Unsigned builds trigger Windows SmartScreen warnings. Configure a code-signing
certificate in the GitHub Actions secrets `WIN_CSC_LINK` and
`WIN_CSC_KEY_PASSWORD` before presenting the installer as a polished public
release. The workflow already passes those values to electron-builder when
they are available.

## Troubleshooting

- Draft releases are invisible to installed apps.
- The package version must be higher than the installed version.
- `latest.yml`, the installer, and the blockmap must come from one build.
- Portable users must download each update manually.
- The repository must remain public for token-free client updates.
- Run `npm run clean:electron` after closing packaged app processes if stale
  output is locked.
